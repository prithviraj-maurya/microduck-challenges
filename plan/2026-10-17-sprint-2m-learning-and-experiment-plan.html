🎯 The north star

The Arena asks the policy to walk a flat 2 m lane as fast as possible. It sweeps forward commands from 0.20 to 1.20 m/s, then repeats its three fastest candidates across five seeds. A fall or timeout costs 50 seconds.

Scoring priority: first finish 5/5. Then lower the mean time. A fast policy that falls is worse than a slightly slower policy that finishes every seed.

The mental model

Observation (61 values) → policy → 14 joint targets → simulated robot → reward → PPO update → checkpoint. An ONNX export packages a selected policy for the Arena. PPO is the update method; reward terms define what behavior gets reinforced.

Learning prompt: while reading env.py, follow one concrete signal end to end. For example, where is forward speed observed, where is speed tracking rewarded, and where would you see that reward in TensorBoard?

▶️ Step 1 · score the policy we have

Run from the repository root. This is an evaluation of the existing ONNX file; it does not train or publish anything.

uv run --group workshop arena score policies/policy_20261017.onnx --event sprint-2m

Save the reported score, number of seeds finished, and selected command speed in the experiment log below. If the command reports a missing package, use the repo’s documented setup and ask before starting any expensive training.

Keep comparison fair: use the same evaluator and machine for local policy comparisons. Physics can drift across CPU architectures, so treat the Space score as the official result.

🧪 Experiment rules of the road

  1. Write the question first: what evidence says this is the problem?
  2. State a prediction: “If I change X, I expect Y because Z.”
  3. Change one thing unless there is a clear reason to test a deliberate combination.
  4. Keep a baseline and name runs clearly. Record code commit, seed, settings, and checkpoint.
  5. Judge with the Arena evaluator. Curves help diagnose; they are not the competition score.
  6. Stop a collapsed run instead of spending compute on a policy that is not recovering.
Known caution: the sprint guide says lane-hold reward at the previously tried settings made walking worse, and tightening head-pose tracking once stopped the gait. Treat those as evidence against repeating those exact changes without a new hypothesis.

📈 Read curves carefully

Healthy clues: episode length trends toward a full episode; falls trend down; speed-tracking reward improves.

Warning clues: total reward rises while speed tracking stays flat; a sharp change near a curriculum stage; NaN terminations.

A reward curve answers “is training behavior changing?” The Arena evaluator answers “does this policy finish quickly under the event rules?” We need both kinds of evidence.

🧠 Concepts to learn

Reward shaping

Rewards are training signals, not the leaderboard metric. If terms compete, a policy may optimize an easy proxy instead of sprint time.

PPO and iterations

Each iteration gathers simulated experience and updates the policy. More iterations do not guarantee steady improvement.

Seed and variance

A seed controls random choices, but GPU simulation and training may still vary. Repeats help tell a robust effect from a lucky run.

Domain randomization

Training varies selected physical properties so a policy can handle variation. Randomization should match what the Arena actually simulates.

Checkpoint vs export

A checkpoint is a training snapshot. ONNX is the portable inference policy the Arena consumes; exporting can include observation normalization.
