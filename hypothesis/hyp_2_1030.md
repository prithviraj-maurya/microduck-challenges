# Hypothesis 2: raise the forward tracking reward to 3.0

## Claim

**Hypothesis:** Raising `forward_reward` from **2.5 to 3.0** will make the policy track faster forward commands more strongly and reduce the 2 m sprint time, while preserving all five finishes.

This is the next direct speed-tracking test. The existing `forward_reward = 2.5` runs both finished 5/5; their best local scores were 3.884 s (training seed 2) and 3.864 s (seed 3), both at checkpoint 1000. The seed 2 run is the clean-provenance comparison for this experiment.

## Change and controlled settings

Change only `params.forward_reward.value` in `src/microduck_challenges/sprint_2m/challenge.toml`:

```toml
[params.forward_reward]
value = 3.0
```

Keep all other environment and training settings unchanged: 4,096 environments, 3,000 maximum iterations, and training seed 2. Do not change `upright_reward`, `step_reward`, the command range, PPO settings, or the environment.

## Baseline and decision rule

- **Baseline:** `forward_reward = 2.5`, seed 2, best checkpoint 1000, **3.884 s**, **5/5 finishes**, winning command **0.70 m/s**.
- **Support the hypothesis:** a checkpoint from this run is at least **0.10 s faster** than 3.884 s on the same local evaluator and finishes **5/5**. Then verify the selected policy on the official Arena before calling it a leaderboard improvement.
- **Refute or leave inconclusive:** no 5/5 checkpoint reaches 3.784 s, or faster results come with a fall. Do not treat higher training reward alone as evidence of a faster sprint.

Score every available checkpoint and choose the best by 5/5 finishes first, then lowest time. The prior runs peaked around iteration 1000 and later checkpoints were often slower, so the final checkpoint is not presumed best.

## What was checked and how

1. Downloaded the completed job artifacts from `prithviraj-maurya/mjlab-sprint2m-microduck-forward30-seed2` into `logs/rsl_rl/`. Confirmed the run directory contained `model_0.pt`, every 250-iteration checkpoint through `model_2750.pt`, `model_2999.pt`, the TensorBoard event file, saved environment/agent config, and `provenance.json`.
2. Exported each checkpoint locally with `publish --dry-run --allow-dirty`. This generated a local ONNX policy for scoring; it did not upload or enter a policy.
3. Ran `arena score <policy.onnx> --event sprint-2m` for every checkpoint. The evaluator swept 21 forward commands from 0.20 to 1.20 m/s, then evaluated the fastest command across five seeds. We chose by 5/5 finishes first and lowest mean time second.
4. Read the TensorBoard event file for mean episode length, falls, XY/yaw velocity error, and weighted velocity-tracking reward, including values around checkpoint 1000 and at iteration 2999. These were used as diagnostics only.

The local export-and-score pattern, from `publish-evals/`, was:

```bash
run_path=../logs/rsl_rl/sprint_2m/2026-11-04_07-11-37_forward30-seed2
for n in 0 250 500 750 1000 1250 1500 1750 2000 2250 2500 2750 2999; do
  uv run --no-sync publish --run "$run_path" --checkpoint "$n" \
    --repo "local/microduck-forward30-cp$n" --dry-run --allow-dirty
  uv run --group workshop arena score \
    "publish-forward30-cp$n/policy.onnx" --event sprint-2m
done
```

The local scorer ran on this Mac’s CPU. Its score is useful for selecting a candidate but is not an official Arena result; the Arena runs on different hardware, and simulated scores can drift between architectures. No policy has been published or entered.
